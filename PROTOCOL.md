# Remote Pi — Protocol & Security

Canonical documentation of the Remote Pi protocol and threat model.
Updated on 2026-07-18.

---

## 30-Second Overview

- **Coding Agent Mesh** running across multiple PCs belonging to the same user
- **Each PC** runs `pi-extension` (Node.js daemon) with **one Pi-key** (Ed25519) stored in system keychain (macOS / Linux / Windows)
- **Mobile phone** acts as the **initial authenticator** (WhatsApp Web style QR code) — after pairing, PCs operate autonomously
- **Owner-key** (Ed25519) lives in mobile keychain (iOS Keychain / Android Block Store), syncing across devices under the same Apple ID / Google Account
- **Relay** (WebSocket) routes messages and stores/verifies signed `mesh_versions` payloads; authorizes direct co-membership
- **Cross-PC routing** uses canonical Pi-keys on the relay

---

## Identities

| Key | Algorithm | Storage | Created By | Used By |
|---|---|---|---|---|
| **Owner-key** | Ed25519 | iOS Keychain (iCloud sync) / Android Block Store (Google sync) | Mobile app on first boot | Signs `mesh_versions`, proves authority to pair/revoke PCs |
| **Pi-key** | Ed25519 | `@napi-rs/keyring` on PC (macOS Keychain / Linux libsecret / Windows Credential Manager). Fallback: `~/.pi/remote/identity.json` (`0600`) | `pi-extension` on first boot | Authenticates WS connection to relay; provides canonical identity for `from_pc` and routing |
| **App-key** | Ephemeral Ed25519 | Mobile app RAM | App per pairing session | Establishes authenticated channel during pairing |

**Technical identity** for each Pi/PC is the raw 32-byte Ed25519 public key. Standard Base64 (RFC 4648) with padding is the canonical representation on wire boundaries. Local nicknames/aliases never replace canonical keys.

**Core constraint**: "1 Pi-key per PC; hardware replacement = re-pairing". No Pi-key migration between machines.

## Protocol Layers

```
┌─────────────────────────────────────────────────────────────────────┐
│  Agent layer       Pi coding agent (future: Claude Code, OpenCode)  │
├─────────────────────────────────────────────────────────────────────┤
│  Envelope          {from, to, id, re, body} — JSONL 5 fields        │
├─────────────────────────────────────────────────────────────────────┤
│  Routing           Local UDS broker / Cross-PC via relay forward    │
│                    Public: [<receiver-local-alias>:]<cwd>@<agent>   │
│                    Local: <cwd>@<agent>; `broker` reserved          │
├─────────────────────────────────────────────────────────────────────┤
│  ACK protocol      received | busy | denied | timeout               │
│                    Broker/BrokerRemote generates ACK without LLM    │
├─────────────────────────────────────────────────────────────────────┤
│  Transport         UDS (local) / WebSocket over TLS (relay)         │
├─────────────────────────────────────────────────────────────────────┤
│  Trust             Ed25519 challenge-response                       │
│                    Owner signatures on mesh_versions                │
└─────────────────────────────────────────────────────────────────────┘
```

## Envelope

Unified format across the system for local (UDS) and cross-PC (relay forward) messaging:

```jsonc
{
  "from": "<sender-name>",
  "to": "<recipient-name>" | ["<r1>", "<r2>"] | "broadcast",
  "id": "<UUID v7 generated by Extension>",
  "re": "<id-of-message-being-replied-to>" | null,
  "body": {}
}
```

Naming:
- **Local**: `<cwd>@<agent>`; `broker` is a reserved local address.
- **Public address**: `[<receiver-local-alias>:]<cwd>@<agent>`.

UUID v7 provides chronological ordering without central coordination.

## ACK Protocol

In unicast mode, each `agent_send` call awaits a fast ACK (default 5s) generated by the local `Broker` or recipient `BrokerRemote` upon delivery — not by the LLM.

| ACK Status | Meaning |
|---|---|
| `received` | Online peer accepted/received message; processed in current or next turn. |
| `busy` | Legacy compatibility: message was dropped by busy leader. |
| `denied` | Peer refused message. |
| `timeout` | ACK did not arrive within timeout window (default 5s). |

Content replies are asynchronous: peers respond with another `agent_send` carrying `re: <original-send-id>`.

## Cross-PC Routing

Cross-PC communication is mediated by the relay.

### Wire WS Frame (Pi-A -> Relay)

```jsonc
{
  "type": "pi_envelope",
  "to_pc": "<Pi-B-key Standard Base64 with padding>",
  "envelope": {
    "from": "<legacy-wire-label-A>:/Users/alice/project@frontend",
    "to": "<legacy-wire-label-B>:/home/bob/project@backend"
  }
}
```

### Relay Delivered Frame (Relay -> Pi-B)

```jsonc
{
  "type": "pi_envelope_in",
  "from_pc": "<Pi-A-key Standard Base64, authenticated>",
  "envelope": { /* forwarded envelope */ }
}
```

## Mesh Membership

`mesh_versions` is the signed registry maintained by the Owner.

```json
{
  "version": 7,
  "issued_at": 1780000000000,
  "owner_pk": "<Owner-key Base64>",
  "members": [
    { "remote_epk": "<Pi-key Base64>", "relay_url": "wss://...", "paired_at": "2026-05-22T...", "nickname": "home" }
  ]
}
```

## Threat Model

### Protected

- **Authenticated pairing**: `pair_request` signed by Owner-sk
- **TLS WebSocket**: Encrypted in transit across network
- **Cross-PC authorization**: Relay checks signed membership before routing
- **Key protection**: System Keychain (macOS / Linux / Windows / iOS / Android)

### Unprotected (Explicit Disclosures)

- **Relay visibility**: Relay sees message routing metadata and plaintext payloads unless end-to-end encryption is enabled (mitigation: self-hosting open-source relay).
- **No E2E claim**: The app makes no claim of zero-knowledge E2E encryption through the public relay.
- **Headless Linux**: File fallback (`0600`) when D-Bus/keyring is unavailable.
